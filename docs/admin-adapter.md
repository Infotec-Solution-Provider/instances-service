# Adaptador da central Infotec

`POST /api/internal/admin` recebe o protocolo Node `src/admin/admin-protocol.ts`.
É necessário configurar `ADMIN_ENVIRONMENT`, `ADMIN_CONTROL_PUBLIC_KEYS` (array JSON de public keys Ed25519, kid, issuer e ambientes autorizados) e `ADMIN_REVISION_KEY` com pelo menos 32 caracteres. Sem configuração, o endpoint falha fechado. O ingresso público deve bloquear esta rota; a assinatura continua obrigatória na rede interna.

Audience `instances` permite catálogo sanitizado de tenants, parâmetros JSON (`tenant`) e conexão CRM (`database`). O inventário dos serviços e SDK não encontrou consumidor tipado de `clients_parameters`: são chaves genéricas armazenadas/retornadas pelo instances-service; o migration-panel copia sua entrada genérica separadamente para parâmetros WhatsApp no provisionamento. Essas chaves aparecem como JSON/segredo somente leitura, aguardando classificação, sem inferir tipo pelo valor e sem permitir inserir novas chaves.

`database` tem catálogo explícito. SAVE grava somente a configuração desejada cifrada em `admin_saved_configurations`; `clients_servers` e os consumidores permanecem inalterados. A criptografia AES-GCM usa chave derivada contextualmente de `ADMIN_SECRETS_KEY`, quando presente, ou `ADMIN_REVISION_KEY`; conservar essa chave e planejar sua rotação junto aos dados cifrados. APPLY valida a revisão e SELECT 1 do novo destino, altera `clients_servers` e registra recibo na mesma transação. Após commit invalida os pools legado e TenantDatabase somente do tenant alvo; transações em andamento drenam, sem receber novas consultas no destino antigo. O recibo permanece COMMITTED com aplicação pendente se a etapa de invalidação/comprovação não terminar.

Audience `users` é aceita exclusivamente para `crm`, `sip-global`, `sip-user`, `webrtc` e ações `getSettings`, `getTargets`, `saveSettings`, `getReceipt`. O users-service encaminha o envelope original; não há SQL arbitrário no contrato nem substituição da identidade do ator. O tenant alvo é separado do administrador Infotec. A persistência remota utiliza uma conexão/transação TenantDatabase para alteração e recibo atômicos. O identificador Infotec do ator não é validado como um operador do CRM alvo. Para registros WebRTC novos, `updated_by=0` identifica administração externa; o recibo registra o ator real.

Aplicar explicitamente `migrations/20261111-admin-operation-receipts.sql` no banco instances e em cada banco CRM participante, e `migrations/20261111-admin-saved-configurations.sql` somente no banco instances. Não há DDL por requisição. As tabelas alteradas e de recibo precisam ser InnoDB; schemas ausentes ou não transacionais impedem a gravação. Defaults/colunas do CRM são lidos no banco alvo; o catálogo local não comprova disponibilidade de coluna. A leitura de parâmetros utiliza o primeiro registro por CODIGO, como as APIs existentes.

Recibos têm operation_id único, fingerprint HMAC e envelope redigido `{actor,tenant,source,target,result}`. Replay compara ator/recurso e conteúdo original; getReceipt compara identidade/recurso e recupera o resultado sem comparar o fingerprint de uma ação diferente. O recibo nunca contém valor secreto. Revisões HMAC incluem o estado persistido, inclusive segredos, sem expô-lo. Conflitos não são repetidos automaticamente.

Validação: `npm run test:admin`; `npm run test:admin:mysql` com `ADMIN_MYSQL_TEST_URL` definido explicitamente para um MySQL local descartável. O teste SQL cria somente bancos `infotec_admin_backend_test_*` e comprova commit, replay, conflito, rollback no erro de recibo, staging cifrado sem alterar destino ativo, e troca dos dois pools somente após APPLY. Testes não usam .env de produção. Preparar/publicar este adaptador e aplicar suas migrations são etapas separadas da implementação.
