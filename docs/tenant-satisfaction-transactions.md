# Contratos transacionais de pesquisa telefônica

`crm.satisfaction.question.write`: batch HMAC com questionId (0 para criar), exatamente pesquisa_satisfacao/pesquisa_satisfacao_avaliacao e um INSERT/UPDATE/DELETE no catálogo. Os comandos permanecem exclusivos de repositórios confiáveis. Não aceita sessão web como assinatura nem amplia SQL arbitrário. Triggers de catálogo são recusadas; as duas tabelas precisam ser InnoDB. Catálogo completo/gaps e chave de avaliações são bloqueados sob REPEATABLE READ; perguntas usadas são recusadas antes da escrita. O serviço de domínio acrescenta CAS e guardas de referências ao SQL. Criar além de 100 perguntas é recusado.

`telephony.schedule.finish` conserva três statements quando não há pesquisa. Com surveyQuestions (1–100 IDs crescentes e descrições), exige três tabelas adicionais e exatamente cinco statements: agenda, historico_cli, recibo, telephony_satisfaction_submissions, pesquisa_satisfacao_avaliacao. O catálogo é comparado sob lock e a faixa de avaliações da agenda também é bloqueada; pesquisas existentes são preservadas. O snapshot usa SQL fixo, history_id null no comando assinado e insertId positivo capturado do histórico pela conexão transacional. O transporte injeta esse ID no parâmetro do snapshot; não usa LAST_INSERT_ID. A contagem das avaliações, IDs de pergunta/agenda e escala 1–5/vazia são conferidos antes de iniciar transação. Todos os INSERTs são obrigatórios.

As três tabelas de pesquisa só são declaradas para finalização com pesquisa. O domínio exige survey apenas para resultado marcado e seu UPDATE inclui CAS da flag. Engines e triggers de todas as tabelas gravadas são verificados pela fundação existente; erro em qualquer statement faz rollback e nunca é tratado como confirmação de commit. Não existem fallback SQL ou retry de escrita. Metadados do driver não são retornados ao frontend.
